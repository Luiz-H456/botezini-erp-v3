Fluxos-chave

Orçamento → Pedido → Produção → Recebimento

  1. Orçamento criado no BudgetEditor (itens, tecidos, plano de pagamento opcional).
  2. Conversão: cria o pedido e chama apply_order_payment_plan — atômico e idempotente por order_id. Se o orçamento já tinha plano, apenas confirma.
  3. As parcelas nascem pré-lançadas: obrigações open com planned_method (PIX/Boleto). Nada foi recebido ainda.
  4. Produção avança por estágios, validando ficha técnica e estoque.
  5. Pedido concluído/entregue → parcelas aparecem em Recebíveis › A disparar.
  6. Disparo manual (pay_obligation) com data e meio escolhidos → recebimento efetivado, saldo bancário atualizado.

Ajuste de plano pós-emissão

  1. revise_order_plan cancela apenas as parcelas em aberto e recria o plano novo.
  2. Parcelas com pagamento ativo são preservadas (imutáveis).
  3. As canceladas ficam auditáveis via cancelled_at / cancelled_reason.

Reconciliação

  1. get_order_reconciliation compara o total do pedido com a soma das obrigações.
  2. Havendo divergência, apply_order_adjustment cria um lançamento novo de ajuste — nunca edita o valor original.

Caixinhas — reserva virtual

  1. saldo_real = soma das contas bancárias ativas.
  2. move_envelope aloca (livre→caixinha) ou libera (caixinha→livre), validando o livre.
  3. fund_envelopes aplica a % automática de cada caixinha sobre um valor-base.
  4. Todo movimento vira linha em cash_envelope_movements (extrato auditável).

Ficha técnica (BOM) alimentando o app

  1. Produto ganha ficha em Cadastros — ou semi-preenchida no QuickCreate (tecido + m/peça).
  2. No orçamento, selecionar o produto pré-preenche o tecido a partir da ficha.
  3. Na produção, a ficha define a baixa de estoque; sem ela o avanço é bloqueado com modal + deep-link para criá-la.

Invariantes do sistema

Fonte única da verdade financeira O estado de uma obrigação vem sempre de obligation_summary. orders.amount_paid e payment_status são legados e não devem ser lidos.
Imutabilidade do valor original financial_obligations.original_amount nunca é alterado. Correções criam novos lançamentos de ajuste.
Idempotência por pedido apply_order_payment_plan não duplica recebíveis se chamado duas vezes para o mesmo order_id.
Atomicidade no banco Operações de dinheiro (pagar, estornar, revisar plano, transferir caixinha) são RPCs transacionais — nunca sequências de chamadas do front.
Categoria unificada global_categories é a fonte oficial (domínios finance/inventory/crm). O campo texto category é fallback histórico, gravado em sincronia com global_category_id.
Pré-lançamento Emitir o pedido não gera recebimento. O boleto/PIX só é efetivado no disparo manual, com data escolhida pelo usuário.
